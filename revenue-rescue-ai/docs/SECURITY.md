# Security notes
Implemented and tested: scrypt password hashing; HMAC-signed httpOnly session cookies (7d, tamper/expiry tests); role gates (`requireAdmin`, `requireOrg`); org_id scoping on all tenant queries with cross-tenant tests; zod input validation; DB-backed rate limits (audit, login, pilot request); SSRF-guarded fetch (scheme/host/IP blocks, re-validated redirects, timeout, size cap); Stripe and Twilio webhook signature verification (timing-safe, replay window for Stripe); webhook idempotency; audit_logs for consequential actions; security headers; no secrets in code; production refuses missing SESSION_SECRET.
Prompt injection: external HTML/SMS/CRM text is data. Only regex-derived flags leave the analyzer; inbound SMS is matched against fixed patterns and stored as inert text; no LLM sees it today. Any future LLM step must receive it inside a delimited data block, output an enumerated schema, and have no tool access beyond validated calls.
**Known gaps / TODO before real customer data:** Postgres row-level security as defense in depth; CSRF beyond Next server-action origin checks and SameSite=Lax for the plain POST forms (`/api/audit`, `/api/pilot-request` are unauthenticated by design); IP rate limiting relies on `x-forwarded-for` from a trusted proxy; encrypt phone numbers at rest; backups/PITR (host-provided); error tracking & monitoring not wired; no MFA on admin; session revocation list; pen test. Not legal advice: compliance rules are in `src/lib/compliance.ts` and `research/`, have an attorney review before any commercial SMS.
